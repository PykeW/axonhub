# 模型管理指南

本指南不再把“模型管理”主要理解成后台里的抽象配置表，而是把它放到 Share / Use 的真实分发链路里：**模型决定一次请求能看到哪些渠道，进而决定它只能使用自己的渠道，还是也可能命中别人的共享渠道。**

## 模型在 Share / Use 里的作用

在当前产品主线里：

- **渠道** 是供给来源
- **模型** 是对外暴露给调用方的稳定入口
- **模型关联** 是把“外部请求的模型名”映射成“哪些渠道可以参与这次分发”

所以模型管理本质上不是“起名字”，而是在定义：

1. 一个请求允许进入哪些候选渠道
2. 这些候选渠道里，哪些属于 `OwnPool`
3. 哪些又能进一步进入 `SharedPool`

## 在请求链路中的位置

模型关联是三层流水线中的**中间步骤**。完整说明请参阅 [请求处理流程](../getting-started/request-processing.md#核心概念三层模型设置)。

简单来说：**API Key Profile 改模型名 → 模型关联选渠道 → 渠道改模型名 → 发给上游**

如果把 Share / Use 目标行为一起放进来，这一步发生在：

- 请求已经拿到生效模型名之后
- `useStrategy` 真正决定先看自有池还是共享池之前
- 现有负载均衡评分之前

## 模型关联真正决定什么

模型关联的作用，不只是“模型能不能用”，而是“这次请求最终能看到哪些供给”。

它至少决定 3 件事：

1. 哪些渠道有资格成为候选
2. 这些渠道上的哪个上游模型可以被实际调用
3. 候选集合在进入 `OwnPool / SharedPool` 过滤前有多大

这也是为什么 Share / Use 方案里，模型暴露和渠道共享必须一起看：

- 一个渠道即使标记为 `shared`
- 但如果它不支持本次请求的模型
- 它仍然不会进入任何人的共享候选集合

## 与 `OwnPool` / `SharedPool` 的关系

对任意用户 `U`，当前文档约定：

```text
OwnPool(U) = ownerUserID == U 的可用渠道（private + shared）
SharedPool(U) = ownerUserID != U 且 visibility == shared 的可用渠道
```

而模型关联发生在这两个池子真正参与排序之前：

- 先根据模型关联找出“哪些渠道理论上支持这次请求”
- 再按 owner、visibility、健康状态、冷却窗口等规则分到 `OwnPool` 或 `SharedPool`
- 最后才由 `useStrategy` 决定先看哪个桶

因此，**模型管理决定候选边界，Use 策略决定消费顺序。**

## 常见模型关联方式

### 1. 指定渠道的指定模型

适合你想把某个模型明确绑定到某个供给来源。

常见场景：

- 某个高价值模型只允许走一条专门渠道
- 某个共享模型只想由特定供应商承接

### 2. 指定渠道的正则匹配

适合在某个固定渠道中批量暴露一类模型。

常见场景：

- 同一个供应商下有一批版本化模型
- 你想减少逐条维护模型映射的工作量

### 3. 所有渠道的指定模型

适合让同一个抽象模型名落到所有支持它的渠道上。

这是最贴近 Share / Use 分发思路的一种配置，因为它能把多个 owner 的同类供给一起纳入候选，再交给后续池子过滤与策略排序。

### 4. 所有渠道的正则匹配

适合用规则批量暴露一组模型，并让所有匹配渠道都参与候选。

这种方式灵活，但也更容易扩大候选范围，所以要特别注意是否会把你不希望暴露给共享分发的模型一起放进来。

### 5. 按标签选择渠道

适合先按渠道标签切分供给，再决定模型暴露范围。

常见场景：

- 按供应商分组
- 按环境分组
- 按共享池治理策略分组

## 优先级

`priority` 值越小，优先级越高。

在当前主线下，优先级更适合理解为：**当多个模型关联都命中时，谁先定义候选集合。**

需要注意：

- 它不直接等于最终命中的渠道顺序
- 最终顺序还会继续受到 `useStrategy`、共享池过滤、`soonest-refresh-first` 和现有负载均衡评分影响

换句话说：

- `priority` 先决定“候选怎么长出来”
- Share / Use 再决定“这些候选先消费哪一边”

## 推荐使用方式

- 想把一个模型固定给特定供给：用“指定渠道的指定模型”
- 想让自有渠道和共享渠道都能承接同一个模型：用“所有渠道的指定模型”
- 想批量暴露一类模型：用正则匹配
- 想先按供给治理分组：给渠道打标签，再按标签选择渠道

## 系统设置

在 **系统设置 > 模型设置** 中，有两个和分发边界相关的常见选项：

| 设置项                 | 说明                                         |
| ---------------------- | -------------------------------------------- |
| 查询所有渠道模型       | 控制 `/v1/models` 是否返回所有渠道中的模型   |
| 模型未找到时回退到渠道 | 控制未命中模型配置时，是否继续尝试按渠道查找 |

从 Share / Use 角度理解：

- “查询所有渠道模型”会影响调用方看到的平台模型面
- “模型未找到时回退到渠道”会影响未显式配置时，系统是否仍尝试从底层渠道供给中找出路由机会

## 常见问题

### Q: 为什么请求提示“模型未找到”？

建议按这个顺序检查：

1. 模型关联是否覆盖了这次请求模型
2. 渠道是否已启用
3. 渠道是否支持关联中指定的模型
4. 渠道是否因为 `private/shared`、owner 过滤或冷却窗口被提前排除
5. 是否又被其他标签、权限或健康状态规则过滤掉

### Q: 为什么我明明有共享渠道，但请求还是没走到它？

常见原因有：

1. 该共享渠道没有暴露这次请求模型
2. 它虽然是 `shared`，但属于你自己，因此不会进入你的 `SharedPool`
3. 当前 `useStrategy` 先消费自有渠道，而且自有渠道已经足够可用
4. 它在桶内排序时被 `soonest-refresh-first` 或现有评分体系排到了后面

### Q: 如何验证模型关联是否生效？

1. 发送测试请求
2. 在控制台查看 Trace
3. 确认请求命中的模型关联、候选池数量和最终渠道

## 最佳实践

1. **模型名保持稳定**：对外优先使用统一、可长期维护的抽象模型名
2. **优先暴露真实想分发的模型**：不要把只给内部测试用的模型混进共享分发入口
3. **优先级保持简单**：先让候选边界清晰，再补备用路径
4. **标签用于治理**：当共享渠道越来越多时，用标签管理供应商、环境或策略组
5. **先验证再放量**：配置后结合 Trace 检查候选集合、池子过滤和最终命中顺序是否符合预期
