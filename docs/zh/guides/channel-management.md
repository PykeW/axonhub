# 渠道配置指南

本指南不再把“渠道”主要当成管理员后台里的抽象配置，而是把它放回你当前最关心的产品主线：**用户上传自己的上游渠道到 Share，平台再基于这些渠道做统一分发**。

## 什么是渠道？

在当前 Share / Use 方向里，渠道首先代表“我贡献给平台的上游连接”。你可以把它理解成：

- 你自己的一个供应商账号入口
- 这个入口支持哪些模型
- 这个入口是否只给自己用，还是愿意共享给别人用

从产品视角看，一个渠道至少要回答 4 个问题：

1. 这是**谁**的渠道？
2. 它支持**哪些模型**？
3. 它是 `private` 还是 `shared`？
4. 它当前是否健康、是否允许刷新？

## 在当前产品里的位置

如果按 [共享/使用 MVP 指南](share-use-mvp.md) 的主线理解：

- **渠道上传** 是 Share 的供给侧入口
- **模型暴露** 决定这个渠道能不能进入某次请求的候选集合
- **可见性** 决定它只属于 owner 的自有池，还是也能进入其他用户的共享池
- **健康 / 刷新状态** 决定它是否还能参与平台分发

也就是说，渠道文档更接近“上传与供给说明”，而不只是传统的“后台配置项说明”。

## 上传自己的渠道

### 当前真实入口

虽然目标产品里会有独立的 `/share` 页面，但当前仓库还处于过渡阶段：

- `/share` 仍然是指南包装页
- 真正的创建、编辑、测试、启用，仍在现有 **渠道管理** 页面完成

所以目前“上传到 Share”的实际操作路径仍是：

1. 进入 **渠道管理**
2. 点击 **新建渠道**
3. 填写基础信息
4. 测试连接
5. 启用渠道
6. 等待后续 Share 字段完整落地

### 基本字段

上传渠道时，当前最重要的是把这些信息准备正确：

- **名称**：便于你自己识别渠道来源
- **类型**：如 OpenAI、Anthropic、DeepSeek
- **Base URL**：上游地址
- **API Key**：上游凭据
- **支持模型**：这个渠道到底能提供哪些模型
- **默认测试模型**：用哪个模型做连通性验证

示例：

**OpenAI 渠道：**

| 字段     | 值                         |
| -------- | -------------------------- |
| 名称     | OpenAI 主账号              |
| 类型     | openai                     |
| Base URL | https://api.openai.com/v1  |
| API Key  | sk-your-openai-key         |
| 支持模型 | gpt-4o, gpt-4o-mini, gpt-5 |

**DeepSeek 渠道：**

| 字段     | 值                               |
| -------- | -------------------------------- |
| 名称     | DeepSeek 国内                    |
| 类型     | deepseek                         |
| Base URL | https://api.deepseek.com/v1      |
| API Key  | sk-your-deepseek-key             |
| 支持模型 | deepseek-chat, deepseek-reasoner |

## Share 语义下的可见性

### `private` / `shared`

在你的目标产品里，可见性不是后台标签，而是平台分发规则的一部分：

| 可见性    | 含义                                                        |
| --------- | ----------------------------------------------------------- |
| `private` | 只进入 owner 自己的渠道池                                   |
| `shared`  | 对 owner 自己仍属于自有渠道池，但也允许进入其他用户的共享池 |

关键规则见 [共享/使用 MVP 指南](share-use-mvp.md#共享池计算规则)：

- 每个用户的共享池都默认排除自己的渠道
- 自己标记为 `shared` 的渠道，不会让自己再从“共享池视角”绕回来使用

### 当前实现状态

当前后端对象层已经有 `ChannelSettings.Share` 默认值和 `private/shared` 枚举，但：

- 渠道 GraphQL schema 还没完整暴露这些字段
- 前端表单和列表还没完整暴露这些字段
- 真正的共享路由和脱敏读取还没有完全接入实体 CRUD

因此，现阶段的正确理解是：

- 这套语义已经是产品目标
- 但真实 `/share` CRUD 还在建设中

## 支持模型与模型映射

### 为什么支持模型很重要

一个渠道是否能被平台分发，前提不是“你上传了”，而是“它真的支持这次请求的模型”。

因此上传渠道时，`supported_models` 和默认测试模型非常关键：

- `supported_models` 决定这个渠道能否进入候选集合
- `default_test_model` 决定你怎么验证这个渠道确实可用

### 模型映射什么时候用

当你想让客户端请求名与实际发给上游的模型名不同，就需要模型映射。

常见场景：

1. **客户端用简化名称**：客户端请求 `gpt-4`，实际发给 OpenAI 的是 `gpt-4o`
2. **统一不同渠道模型名**：让多个供应商暴露统一模型入口
3. **旧版兼容**：客户端请求旧模型名，系统自动映射到新版

在渠道的 **Settings** 中添加映射：

| 客户端请求的模型名 (from) | 实际发给上游的模型名 (to) |
| ------------------------- | ------------------------- |
| gpt-4o-mini               | gpt-4o                    |
| claude-3-sonnet           | claude-3.5-sonnet         |

**注意**：目标模型（to）必须在 `supported_models` 列表中。

## 测试、启用与刷新

### 测试连接

上传后，先测试再启用：

1. 在渠道列表中找到刚创建的渠道
2. 点击 **测试**
3. 等待测试结果
4. 成功后再启用

### 启用渠道

测试通过后，点击 **启用**，渠道状态变为 **活跃**，这才意味着它未来有资格进入请求候选。

### 5 小时刷新窗口

在 Share / Use 主线里，刷新窗口是平台分发可用性的一部分，而不是纯后台细节：

- 每个共享渠道独立计算刷新窗口
- 第一次刷新应允许立即执行
- 刷新成功后，下一次允许刷新时间应顺延 5 小时
- 并发刷新同一渠道时，应只有一个成功

当前渠道管理页还没有直接展示 `nextRefreshAt` 或刷新冷却状态，所以现阶段不要把它理解成“已经完整可操作的后台字段”；应以 [共享/使用 MVP 指南](share-use-mvp.md) 的目标规则为准。

## 当前推荐操作流程

在独立 `/share` 页面完全落地前，推荐按下面顺序操作：

1. 在 **渠道管理** 页面完成渠道基础信息、Base URL、API Key、支持模型配置
2. 在 **模型管理** 页面确认模型暴露是否正确
3. 用 **测试** / **启用** 验证渠道是否稳定可用
4. 如果准备未来进入共享池，优先确保支持模型、默认测试模型、健康状态和敏感凭据管理清晰

## Base URL 特殊配置

### 默认地址

| 服务商    | 默认 Base URL                                      |
| --------- | -------------------------------------------------- |
| OpenAI    | `https://api.openai.com/v1`                        |
| Anthropic | `https://api.anthropic.com`                        |
| DeepSeek  | `https://api.deepseek.com/v1`                      |
| Gemini    | `https://generativelanguage.googleapis.com/v1beta` |

### 自定义地址

如果使用代理或私有化部署，可以修改 Base URL。

**禁用版本号自动追加**：在 URL 末尾加 `#`

```
https://custom-proxy.example.com/api#
# 实际请求: /api/messages（不会自动加 /v1）
```

**完全原始模式**：在 URL 末尾加 `##`

```
https://custom-gateway.example.com/api##
# 实际请求: /api（不会加版本号和端点路径）
```

## 常见问题

### Q: 测试连接失败怎么办？

- 检查 API Key 是否正确（复制时是否有多余空格）
- 确认 Base URL 是否可访问
- 检查服务商账户是否有余额/额度

### Q: 请求时提示"模型未找到"？

- 确认模型已在渠道的 `supported_models` 中
- 检查模型映射配置是否正确
- 确认渠道已启用

### Q: 如何设置多个 API Key？

在 `credentials.api_keys` 中列出所有 Key，系统会自动轮询使用。

### Q: API Key 被禁用了怎么恢复？

进入渠道详情，在 **禁用列表** 中找到该 Key，点击 **恢复**。
